# Session 2026-10-21/22 (+ rerun 10-24): CPU utilisation, memory capacity, and the CUDA caching flag

**Board:** Jetson Orin Nano 8 GB, JetPack 6.2 (L4T R36.4.7), 15 W mode, torch 2.11.0, transformers 4.30.2.
**Sessions:** 2026-10-21 16:10 to 2026-10-22 ~01:00; rerun with mpstat + jtop on 2026-10-24 (§10).
**Commits:** `cb65ccd` (evidence) and `eecc846` (the change), pushed to `origin/main`.

The session started from two questions from the professor:

1. Does the software use the Jetson's multiple CPU cores? Check with jtop / `mpstat -P ALL`.
2. Is memory capacity a big challenge? Check with `tegrastats`, and see the edomtech article on
   Jetson memory optimisation.

Answering them turned up the biggest latency lever this project has found. It was A/B-tested,
soaked for 4h20m, and **shipped**: the PyTorch CUDA caching allocator is back on. Post-cut latency
is roughly halved, with byte-identical translations.

## 1. Headline results

> 10-24 rerun at flag=0 (§10): CPU 59% busy while signing, 26% during translation; decode is now bound by one CPU core; RAM 93-95%, and an OOM crash at load with Firefox open.

| | before (flag=1, shipped until 10-22) | **now (flag=0, shipped 10-22)** |
|---|---|---|
| post-cut latency, sequential, median | 9.3-10.0 s | **5.24 s** |
| post-cut p95 / max | 14.1-18.0 / 19.5 s | **7.97 / 9.37 s** |
| ByT5 decode, ms per step | 60-139 (varies by day) | **38.5-40.5 (stable)** |
| drain after the cut, mean | 3.8-4.6 s | **1.78 s** |

| overlapped post-cut median | 57-61 s | **26.0 s** |

- **CPU:** multi-core is used, but the CPU is never saturated. 66% of the 6 cores are busy while
  signing, 26% during translation. CPU is not the bottleneck.
- **Memory:** this is the binding constraint. RAM peaks at 7.0-7.3 of 7.6 GB in every run, swap
  reaches 0.5-1.5 GB, and the largest free contiguous blocks are 4 MB from start to finish.

### 2.3 New material worth adding

1. **The caching-allocator result is a good edge-deployment story.** One environment variable,
   historically set to dodge an NVML assert on an older torch, cost ~2x on decode and ~1.9x on
   end-to-end post-cut latency. It also accelerated the within-process memory decline about 6x per
   utterance. Its cost varied day to day (60 → 105 → 139 ms/step on the same box) while flag=0 stayed
   at ~40. Lesson: on unified-memory boards, raw cudaMalloc/cudaFree per tensor is expensive and
   state-dependent.
2. **Utilisation table (§3.1):** a direct answer to "does it use the cores?" Reviewers of an
   edge paper will ask it.
3. **Acceptance rate at live pace** (59% at a 1.5 s gap) is the honest "signer does not wait"
   number, alongside the queue-depth table.
4. **Fragmentation:** OOMs on Jetson are gated by contiguous NvMap blocks, not free MB (10-08
   RESULT 5). tegrastats showed `lfb` at 1×4 MB in every run this session, under both flag settings.
5. **Threats to validity:** replayed OpenASL clips through the real live worker, not live
   signing. No head/tail trim in replay. The camera ran at 15 fps at night (low light) instead of 30.

## 3. Professor's question 1: CPU / multi-core usage

### 3.1 Method

- **jtop / mpstat were not used on 10-21** (sysstat was not installed; jtop was wrongly assumed to
  be unscriptable). **Both were used in the 10-24 rerun (§10):** sysstat is now installed, and jtop
  logs from its Python API via `latency_runs/jtop_log.py`.
- **Used instead:** `latency_runs/cpu_profile.py`. It runs the real live worker (`latency_probe.py`,
  real camera open, OpenASL clips replayed at wall-clock rate) and samples every 0.5 s:
  - per-core busy % from `/proc/stat` (exactly what `mpstat -P ALL` computes);
  - CPU seconds **per thread** from `/proc/self/task/*/stat`, labelled with the Python thread
    name. mpstat cannot show this.
- `tegrastats --interval 500 --logfile …` ran alongside for per-core load, GPU (GR3D), RAM, swap,
  lfb, temperature and power.
- **Sampler overhead was checked:** 139.2 vs 139.2 ms/step decode with and without it (8 clips).

### 3.2 Results (40-clip set, flag=1, i.e. the config at the time)

Cores busy, mean over 6 cores, sequential condition:

| phase | cores busy | per-core | where the CPU goes |
|---|---|---|---|
| capture (signing; perception + DINOv2 streaming) | **3.95 / 6 (66%)** | 64-68% each, evenly | MediaPipe C++ graph threads 2.36 cores, embed 0.25, native pools 0.24, camera loop 0.17 |
| drain (after the cut) | 2.61 / 6 (43%) | 41-47% | MediaPipe 0.59, embed 0.54 |
| ByT5 (SHuBERT + decode) | **1.57 / 6 (26%)** | 17-43% | translation worker 0.72 (never > 0.9 of a core) |
| overlap condition, whole run | 2.46 / 6 (41%) | 39-52% | MediaPipe 0.86, worker 0.36 |

GPU load (tegrastats GR3D, sequential): capture 38%, drain 55%, ByT5 48%, idle 33%.

**Conclusions:**
- **Yes, the software uses multiple cores.** MediaPipe runs ~70 internal threads and loads all 6
  cores evenly while signing. There are 2 perception workers, and each frame runs pose, hand and
  face concurrently.
- **The CPU is never saturated.** About 2 cores are idle even during capture.
- **ByT5 decode is single-threaded:** one thread at ~0.7 of a core with the GPU ~half busy. It is a
  serial loop of small kernel launches plus (at flag=1) per-tensor cudaMalloc/cudaFree. More cores
  cannot speed it up; the caching allocator did (§5).
- **New: the drain is mostly the DINOv2 embed stage, not MediaPipe.** MediaPipe CPU drops to zero
  1.19 s (mean) after the cut. The remaining 3.42 s of a 4.61 s mean drain (flag=1) is the single
  `embed` thread catching up at ~0.6 core with the GPU at ~55%. That thread does crop, then per-crop
  PIL resize/normalise, then DINOv2. Neither resource is saturated, so it is serial
  CPU-then-GPU work. The 10-08 notes' wording "drained MediaPipe backlog" is wrong; the column name
  "perception + DINOv2 done" was right. At flag=0 the drain fell to 1.78 s mean anyway.

### 4.2 Conclusions

- **Memory is the binding constraint, much more than CPU.** Every run sits at 92-96% RAM with swap
  in use.
- **Clips get refused.** At live pace the backlog guard (`MAX_RETAINED_FRAMES=450`) refuses
  clips: 30 of 40 at flag=1 on 10-21, 41% overall at flag=0. In longer sequential sessions at
  flag=1, the free-memory guard (`MIN_AVAILABLE_MB=350`) refuses clips once memory has drifted down.
- **Fragmentation is constant.** `lfb` (free 4 MB blocks) reads 1 in every run. On Jetson a large
  CUDA allocation needs contiguous NvMap memory, which is why the 10-08 OOMs hit with >1 GB
  "available".
- **Within-process memory decline is mostly the flag.** Available memory at cut fell ~1,230 →
  ~340 MB over 40 utterances at flag=1, and ~1,270 → ~800 MB over 120 utterances at flag=0. That is
  ~6x slower per utterance, and no longer reaches the 350 MB floor. Slowed, not eliminated.
- **Power and thermals are fine.** Flag=0 draws more (12-14 W vs ~10.5 W) because it does more work
  per second, still under the 15 W budget. Tj stays at 56.6 °C max. (The known silent power-off
  happens at ~5 W idle, so it is unrelated.)

### 4.3 The desktop's share, and the edomtech article

Non-pipeline processes held ~2.5 GB RSS (an overcount, since shared pages are summed): gnome-shell
362 MB, claude CLI 319, Xorg 180, gnome-software 98, packagekitd 56, dockerd+containerd 68,
tracker, evolution, goa and others.

The article's suggestions, mapped to this project:

| article suggests | applies here? |
|---|---|

| host instead of containers (~70 MB) | n/a, not containerised (though dockerd is running and could be stopped) |

| quantise (INT4/FP8/W4A16) | **already ruled out**: decode is dispatch-bound, not weight-bound (2026-08-24); weights are already bf16/fp16 |
| offload preprocessing to PVA/ISP/NVENC | not explored; the per-crop PIL preprocessing in the embed thread is the obvious candidate |

## 5. The caching-flag discovery, A/B, soak, and ship

### 5.1 How it was found

During the CPU study, decode ran 110 ms/step against 73 on 10-08, with the same clips and order.
Clocks, power mode, thermals and library versions all matched, and the sampler was ruled out. Then
the standalone benchmark `benchmarks/nocache_ab.py` was rerun:

| ms/step | 08-24 | 10-08 | 10-21 |
|---|---|---|---|
| flag unset / 0 | 38.8 | 37.0 | 40.9 / 40.1 |
| `PYTORCH_NO_CUDA_MEMORY_CACHING=1` | 99.7 | 60.0 | 104.7 |

At flag=1 every tensor allocation is a raw cudaMalloc/cudaFree (driver/NvMap work on the CPU), and
its cost depends on box state. The 10-08 note that "the flag's cost halved" was a fluke, not a
torch change.

### 5.2 Matched A/B (`latency_runs/flag_ab/`)

Control → variant → control, fresh process per cell, same 40 clips in the same order (seed 1001).

| cell | measured / 40 | median | p95 | decode ms/step | drain | min avail MB |
|---|---|---|---|---|---|---|
| seq flag=1 | 40 | 9.96 | 18.03 | 73.7 | 3.92 | 267 |
| **seq flag=0** | **40** | **5.20** | **8.47** | **40.0** | **1.73** | **545** |
| seq flag=1 | 27 (13 declined, low MB) | 9.49 | 14.09 | 73.2 | 3.83 | 248 |
| ovl flag=1 | 11 | 60.76 | 99.17 | 79.2 | 1.88 | 279 |
| **ovl flag=0** | **19** | **28.22** | **64.29** | **40.8** | 1.09 | 248 |
| ovl flag=1 | 11 | 61.08 | 99.31 | 77.9 | 1.91 | 221 |

- Text: 0 of 40 differ, sequential.
- Overlap had 2 of 9 differ. Both clips were deferred (non-streamed) at flag=1 and streamed at
  flag=0, which is the known 10-08 RESULT 8 worker-count effect, not the allocator.

### 5.3 Soak (`latency_runs/soak/`, 2026-10-21 20:28 → 10-22 00:48)

15 fresh processes, alternating sequential (the 40-clip set ×3 = 120 utterances per process) and
overlap (40), new seed each.

- **1,240 utterances, 1,126 translated, 114 declined (all overlap, backlog), 0 errors, 0 OOM, 0 NVML
  asserts, 0 aborts, every exit 0, 15 model loads.**
- Sequential medians per pass: 5.15-5.34 s, p95 7.9-8.4 s, decode 38.5-40.5 ms/step. **No drift
  over 4 hours.**
- **960 sequential translations, 0 differ** from each clip's first occurrence.

### 5.4 What shipped (`eecc846`, pushed)

- `auto_segment_v5.py`: `os.environ.setdefault("PYTORCH_NO_CUDA_MEMORY_CACHING", "0")`, with a
  comment giving the evidence and the revert. The `_release_cuda_cache()` docstring is updated:
  it is no longer a no-op.
- `live_worker_probe.py`, `latency_runs/latency_probe.py`, `latency_runs/capture_env.sh`: same
  default, so measurements test what ships.
- README: step 8 rewritten (nothing to set; `=1` is the fallback if the NVML assert returns); the
  step 9 latency expectation changed to ~5 s median / ~8 s p95; a config-table row added.
- **Verified with the variable unset:** 3 clips at 3.8-7.8 s post-cut, drain 1.2-1.8 s.
- **Deliberately unchanged:** `benchmarks/byt5_split.py` and the other benchmarks still set `=1`, to
  stay comparable with their recorded numbers.
- **Revert without editing code:** `export PYTORCH_NO_CUDA_MEMORY_CACHING=1`.

### 10.1 Professor's question 1: does it use the multiple cores?

**Yes, but the CPU is never the bottleneck.** Sequential phases (per-thread sampler, `/proc/stat`):

| phase | cores busy, flag=0 (10-24) | flag=1 (10-21) | per-core | main consumer |
|---|---|---|---|---|
| capture (signing) | **3.56 / 6 (59%)** | 3.95 (66%) | 57-63% each, evenly spread | MediaPipe C++ threads 2.44 cores |
| drain (after the cut) | 2.73 / 6 (45%) | 2.61 (43%) | 45-47% | MediaPipe 1.68 cores |
| ByT5 (translation) | **1.55 / 6 (26%)** | 1.57 (26%) | 18-43% | translation worker 0.90 cores |
| overlap, whole run | 3.29 / 6 (55%) | 2.46 (41%) | 52-59% | MediaPipe 1.93, worker 0.38 |

mpstat, whole-run average busy % per core (100 - %idle, 1 s samples):

| | all | cpu0 | cpu1 | cpu2 | cpu3 | cpu4 | cpu5 |
|---|---|---|---|---|---|---|---|
| sequential (574 s) | 47.0 | 43.6 | 44.0 | 43.7 | 46.2 | 51.4 | 53.0 |
| overlap (389 s) | 53.6 | 50.9 | 51.2 | 51.2 | 52.3 | 56.9 | 59.3 |

**New finding at flag=0: ByT5 decode is now bound by one CPU core.** The translation worker thread runs
at a median 0.98 of a core during translation, and 84% of its samples are above 0.9 (at flag=1: ~0.72,
never above 0.9). With the caching allocator on, the cudaMalloc overhead is gone and the serial Python
decode loop, which launches kernels one step at a time, saturates the single core it runs on. GPU load
stays at about a third (jtop mean 34%). Five cores sit mostly idle meanwhile. More cores cannot help a
serial loop; a faster single core or fewer per-step launches (e.g. CUDA graphs) would.

### 10.2 Professor's question 2: is memory a big challenge?

**Yes, memory is the binding constraint.**

| | sequential | overlap |
|---|---|---|
| RAM peak (tegrastats, of 7,620 MB) | 7,131 MB | 7,239 MB |
| RAM peak / mean (jtop) | 93.6% / 86% | 95.1% / 85% |
| swap peak (jtop) | 771 MB | 1,075 MB |
| min MemAvailable (probe) | 445 MB | 282 MB |
| lfb (largest free blocks), tegrastats | 1×4 MB in 257 of 1,132 samples | 1×4 MB in 172 of 768 samples |
| NvMap allocation failures (`error 12`) | 1 (during warmup, recovered) | 0 |
| GPU load mean (jtop) | 34% | 37% |
| power mean / max, Tj max | 8.1 / 12.4 W, 55.0 °C | 8.7 / 14.0 W, 56.2 °C |

**Direct evidence from this session:** the first attempt, with Firefox (~2 GB across its processes) and
Update Manager open, **crashed with CUDA out-of-memory while loading the DINOv2 weights**, before the
first clip. Free memory looked like ~3.8 GB, but jtop showed `lfb 0`, meaning no free contiguous
block. After closing them and running `drop_caches`, it loaded fine. The pipeline does not fit alongside
a browser on this board. That is the clearest single answer to the question, and it fits the 10-08
finding that OOMs are gated by contiguous NvMap blocks, not free MB.

### 10.4 For the professor / paper

- Utilisation table (§10.1) answers "does it use the cores": yes, all 6, evenly, while signing. It never
  saturates. Translation is serial and uses one core.
- Memory (§10.2): 93-95% RAM, swap in use, lfb down to one 4 MB block, and a reproducible OOM with a
  browser open. Running headless / trimming the desktop (from the edomtech article) is still the one
  untested lever.
- The single-core-bound decode at flag=0 is new and worth a sentence. It moves the next possible
  speedup from memory allocation to per-step launch overhead.

### 10.8 Why translation uses one core (for the write-up)

ByT5 writes the output one byte at a time and each byte depends on the previous ones, so decode is
~80 strictly sequential steps of ~40 ms. Each step is mostly CPU work in a single Python/PyTorch
thread launching hundreds of small GPU kernels in order on one CUDA stream; the GPU finishes each
kernel quickly and waits for the next launch (GPU ~35% busy, one core ~95%). Perception threads are
idle because no new frames arrive after the cut. More cores cannot help one sentence. Already closed:
quantisation (dispatch-bound, not weight-bound) and `torch.compile` on the decoder (1.22x live, but lost
2 of 4 clips to OOM under overlap, 2026-08-24). Untested: CUDA-graph capture of the decode step, which
targets launch overhead directly but would also cost memory, the binding constraint.

OOMs on this board are gated by contiguous NvMap blocks, not free MB (10-08 RESULT 5; §10.2 load-time OOM
with ~3.8 GB "available"). Anything that frees memory also reduces fragmentation pressure and should
lower the backlog refusals (41% at live pace) and the in-process memory decline.
